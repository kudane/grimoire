# INDEX

**Index (ดัชนี)** เปรียบเสมือนสารบัญหนังสือ ที่เป็นตัวช่วยให้ค้นหาข้อมูลเจอได้ไวขึ้น

> **Index** หลักๆ มี **2 ประเภท** คือ `Clustered Index` และ `Non-Clustered Index`

---

## 1. Clustered Index (ดัชนีแบบจัดเรียงข้อมูลจริง)

* ข้อมูลในตารางจะถูกเรียงลำดับทางกายภาพ (`Physical`) ตามคอลัมน์ที่ทำ `Clustered Index`
* **1 ตาราง (`Table`)** จะมี `Clustered Index` ได้แค่ **1 ตัวเท่านั้น**
* โดยปกติ เมื่อสร้าง `Primary Key` (คีย์หลักของตาราง) ระบบจะสร้าง `Clustered Index` ให้คอลัมน์นั้นอัตโนมัติ

---

## 2. Non-Clustered Index (ดัชนีแบบชี้เป้า)

* โครงสร้างข้อมูลถูกสร้างแยกออกมาต่างหากจากข้อมูลจริง
* จัดเก็บเฉพาะ **ค่าของคอลัมน์ที่เราทำ Index** คู่กับ **ตัวชี้เป้า (`Pointer` หรือ `Bookmark`)** เพื่อบอกตำแหน่งว่าข้อมูลเต็มๆ บรรทัดนี้อยู่ที่ไหนในตารางจริง
* **1 ตาราง** สามารถมี `Non-Clustered Index` ได้ **หลายตัว**

---

## 3. Usecase จริง: การออกแบบ 1 Table

สมมติเราต้องออกแบบตารางเก็บข้อมูลการสั่งซื้อสินค้า **`Orders`** ในระบบ `E-Commerce`

### โครงสร้างตาราง:

* `OrderID` — รหัสใบสั่งซื้อ (เป็นตัวเลขรันอัตโนมัติ)
* `CustomerID` — รหัสลูกค้า
* `OrderDate` — วันที่สั่งซื้อ
* `TotalAmount` — ยอดเงินรวม

### การออกแบบ Index ที่เหมาะสม:

1. **`Clustered Index`**
* **เลือกใช้กับ:** `OrderID` (ตั้งเป็น `Primary Key`)
* **เหตุผล:** เป็นตัวเลขที่รันไปข้างหน้าเรื่อยๆ ข้อมูลใหม่จะถูกเขียนต่อท้ายเสมอ ไม่เกิดปัญหา `Page Split` และบ่อยครั้งที่ระบบต้องดึงข้อมูลใบสั่งซื้อตาม ID นี้ตรงๆ


2. **`Non-Clustered Index` (ตัวที่ 1)**
* **เลือกใช้กับ:** `CustomerID`
* **เหตุผล:** ผู้ใช้มักเปิดดูประวัติการสั่งซื้อของตัวเอง (เช่น ค้นหาว่าลูกค้ารหัส A001 ซื้ออะไรไปบ้าง) การมีดัชนีชี้เป้าที่รหัสลูกค้า จะช่วยให้หาใบสั่งซื้อของลูกค้ารายนี้เจอทันที โดยไม่ต้องสแกนหาทั้งตาราง


3. **`Non-Clustered Index` (ตัวที่ 2)**
* **เลือกใช้กับ:** `OrderDate`
* **เหตุผล:** ทีมบัญชีหรือการตลาดมักดึงรายงานสรุปยอดขาย "ตามช่วงเวลา" (เช่น ดึงออเดอร์ของเดือนที่แล้ว) ดัชนีตัวนี้จะช่วยให้กวาดข้อมูลตามวันที่ได้รวดเร็ว
