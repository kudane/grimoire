# Database Key Types & Page Split

คู่มือสรุปบทบาทของ Key และ Constraint แต่ละประเภทในระบบฐานข้อมูล พร้อมวิเคราะห์ผลกระทบต่อการเกิด **Page Split** อย่างละเอียด

---

## ประเภทของ Key (Database Keys)

### 1. Unique Key (คีย์ข้อมูลห้ามซ้ำ)

* **หลักการทำงาน:** ควบคุมไม่ให้ข้อมูลในคอลัมน์ซ้ำกัน เช่น `email` หรือ `phone_number`
* **ผลกระทบต่อ Page Split:** **ส่งผลโดยตรง**
* **สาเหตุ:** เบื้องหลังระบบจะสร้าง Index (หน้าสารบัญ) ให้อัตโนมัติเพื่อใช้ตรวจจับข้อมูลซ้ำได้อย่างรวดเร็ว
* **กรณีตัวอย่าง (Use Case):**
* ระบบจัดเก็บอีเมลลูกค้า เมื่อมีผู้ใช้สมัครใหม่ด้วยอีเมลขึ้นต้นด้วยตัว `A` ระบบจำเป็นต้องนำข้อมูลไปแทรกไว้ในหน้าสารบัญหมวด A
* หากหน้าข้อมูล (Page) ของหมวด A เต็ม ระบบจะบังคับแยกหน้าข้อมูลทันที (**Page Split**)



> **Key Takeaway:** แม้ตัวตารางหลักจะไม่แยกหน้า แต่ตัว B-Tree Index ของ `Unique Key` จะเกิด Page Split แน่นอนหากข้อมูลใหม่มีค่าที่ต้องแทรกตรงกลาง

---

### 2. Composite Key (คีย์ผสม)

* **หลักการทำงาน:** นำตั้งแต่ 2 คอลัมน์ขึ้นไปมารวมกันเพื่อทำหน้าที่เป็น `Primary Key` หรือ `Unique Key` เช่น `branch_id + receipt_no`
* **ผลกระทบต่อ Page Split:** **ส่งผล แต่ระดับความรุนแรงขึ้นอยู่กับ "คอลัมน์แรก" เป็นหลัก**
* **สาเหตุ:** ระบบจัดเรียงข้อมูลโดยยึดลำดับจากคอลัมน์แรกก่อนเสมอ หากคอลัมน์แรกซ้ำกันจึงจะพิจารณาคอลัมน์ถัดไป
* **กรณีตัวอย่าง (Use Case):**
* **กรณีปลอดภัย (โอกาสเกิด Split ต่ำ):** ใช้ค่าที่เพิ่มขึ้นตามเวลาขึ้นก่อน เช่น `YYYYMMDD + customer_id` ข้อมูลใหม่จะถูกเขียนต่อท้ายเสมอ (Append-only)
* **กรณีเสี่ยงสูง (เกิด Split บ่อย):** ใช้ค่าที่ไม่เรียงลำดับขึ้นก่อน เช่น `customer_id + date` เมื่อลูกค้าเก่าสั่งซื้อ ข้อมูลจะวิ่งไปแทรกตรงกลางของกลุ่มข้อมูลเดิม หากหน้านั้นเต็มจะเกิด Page Split ทันที



---

### 3. Foreign Key (คีย์นอก / คีย์อ้างอิง)

* **หลักการทำงาน:** ทำหน้าที่ตรวจสอบความถูกต้อง (Referential Integrity) ว่าข้อมูลที่ระบุมีอยู่จริงในตารางปลายทางหรือไม่
* **ผลกระทบต่อ Page Split:** **โดยลำพังตัวมันเองไม่ส่งผล (0%)** แต่สิ่งที่ผูกมาด้วยมักจะส่งผล
* **สาเหตุ:** ตัว `Foreign Key` ไม่ได้บังคับจัดเรียงข้อมูลใหม่ แต่ในทางปฏิบัติ ผู้ดูแลระบบ (DBA) มักจะสร้าง Index กำกับไว้เสมอเพื่อรองรับการเชื่อมข้อมูล (`JOIN`)
* **กรณีตัวอย่าง (Use Case):**
* เมื่อมีการสร้าง Index บนคอลัมน์ `Foreign Key` หากค่าคีย์ที่บันทึกเข้ามาเป็นแบบสุ่ม (Unordered / Random) Index Page ของ Foreign Key ตัวนั้นก็จะเกิด Page Split ตามปกติ



---

## เงื่อนไขและกฎข้อบังคับ (Constraints)

### 1. CHECK Constraint (เงื่อนไขตรวจสอบข้อมูล)

* **หลักการทำงาน:** ตรวจสอบความถูกต้องของข้อมูลตามตรรกะที่กำหนด เช่น `age >= 18` หรือ `price > 0`
* **ผลกระทบต่อ Page Split:** **ไม่ส่งผลเลย (0%)**
* **สาเหตุ:** ตรวจสอบบนหน่วยความจำ (`RAM`) ก่อนเขียนข้อมูลลงดิสก์ หากไม่ผ่านเกณฑ์ระบบจะปฏิเสธคำสั่งทันที (`Error`) โดยไม่มีการเขียนข้อมูลลงหน้ากระดาษ

> **ข้อสรุป:** `CHECK Constraint` ไม่มีการสร้าง Index และไม่ยุ่งเกี่ยวกับการจัดเรียงตำแหน่งข้อมูลบนดิสก์ จึงไม่ก่อให้เกิด Page Split

---

### 2. ภาพรวมของ Database Constraints

คำว่า `Constraint` คือนิยามหมวดหมู่ของกฎที่ใช้รักษาความถูกต้องของข้อมูล (`Data Integrity`) สามารถแบ่งกลุ่มตามผลกระทบต่อการเกิด **Page Split** ได้ 2 กลุ่มหลัก:

#### กลุ่มที่ 1: บังคับสร้าง Index (ส่งผลต่อ Page Split)

* **Primary Key Constraint:** บังคับค่าต้องไม่ว่าง ห้ามซ้ำ และจัดเรียงข้อมูลหลักบนดิสก์ (สร้าง Clustered/Unique Index เสมอ)
* **Unique Constraint:** บังคับห้ามซ้ำ (สร้าง Non-Clustered Index ให้อัตโนมัติ)

#### กลุ่มที่ 2: ตรวจสอบความถูกต้องเท่านั้น (ไม่ส่งผลต่อ Page Split)

* **CHECK Constraint:** ตรวจสอบตรรกะของค่าข้อมูล
* **NOT NULL Constraint:** ตรวจสอบว่าต้องมีค่า (ห้ามเป็นค่าว่าง)
* **DEFAULT Constraint:** กำหนดค่าเริ่มต้นให้อัตโนมัติกรณีไม่มีการส่งข้อมูลเข้ามา
